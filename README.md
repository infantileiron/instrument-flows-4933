# 吹桐民乐 · 跨馆器材调借透视

把三家排练馆的电子签领与冲销凭据编成馆际流向矩阵。分析员提交计算，业务复核席对照签名和边际后发布净流报告。

## 使用场景

吹桐民乐是一个模拟的社区民乐团，三个排练馆共享总库的笙和各分馆的鼓、锣。器材交接由馆点负责人在电子交接单上确认，调借分析员在台账登记。原有流程靠群聊追问与手工合并 Excel，复核时难判断一笔撤销对应哪张签领单，同族器材的反向借用容易被相加，月初冲掉上期凭据也容易在结账时漏记。

上游是交接单与更正联，本项目负责签名记账、保留冲销对照、冻结透视参数与计算结果。下游的馆务观察席用已发布的报告核对下一轮排练需要调配的方向。报告核算凭据上的件数。

| 席位 | 账号 / 本地演示口令 | 权限与典型动作 |
| --- | --- | --- |
| 调借分析 `analyst` | `analyst` / `ScoreAnalysis12!` | 读名录、台账与全部运行，签领、全额冲销、保存方案版本、提交计算和导出结果 |
| 业务复核 `reviewer` | `reviewer` / `ScoreReview12!` | 查阅台账及全部运行，核验凭据、查审计、发布完成的报告、导出 |
| 馆务观察 `observer` | `observer` / `ScoreObserve12!` | 查阅名录、凭据、已发布报告关联的方案版本，筛选和导出已发布报告 |

## 复核剧本

以下为模拟的 2026 年 11 月 16 日馆务复核。`2026-11-02` 到 `2026-11-15` 的 v1 初始报告含 12 份生效凭据，签领 38 件、冲销 5 件。其中 `CT-1103-02` 误录的 5 支笙由 `CX-1111-01` 冲销，吹桐→雁回剩余 8 支笙，反向为 3 支。

1. 09:00，分析员许听澜打开「馆藏名录」，确认吹桐总馆 `CT`、雁回分馆 `YH`、竹水分馆 `ZS`。
2. 09:05，许听澜按模拟交接单 `CT-1115-91` 补录吹桐→雁回的 6 支笙，生效日为 `2026-11-15`，在「凭据台账」看到验签通过。
3. 09:10，交接班确认该补录属于误录。许听澜在「冲销核对」登记 `CX-1115-91` 并选择原签领，仍以 `2026-11-15` 生效。两笔均保留，合计影响为 0。
4. 09:15，许听澜在「透视方案」保存「十一月上半月调借」v2，将起日从 `2026-11-02` 改为 `2026-11-01`，末日保持 `2026-11-15`，包含全部器材。
5. 09:17，点击 v2「运行透视」。后台基于已冻结的凭据快照计算。`CX-1101-01` 将 10 月签领过的 4 面鼓在 11 月单独冲销。
6. 09:20，业务复核席陆清扬检查 v2：15 份凭据、签领 44 件减冲销 15 件等于有效调借 29 件。核对三馆净流 `+4 / −2 / −2`，合计 0 件。
7. 09:24，陆清扬切到「鼓」，看到吹桐→竹水为 `−4`、反向为 `2`，两向相抵为 `0`。展开快照凭据编号，确认在窗口中只列出 11 月冲销凭据；后台另外取 10 月原签领验签。
8. 09:30，陆清扬点击「复核通过并发布」，观察席林至远打开同一份报告并下载 `flow-<运行编号>.csv`，按器材族、馆对核对交接件数。

## 计算口径

- 每份凭据由服务端以 HMAC-SHA256 对编号、类型、原凭据 ID、方向、器材族、数量、生效日、签领账号和事由签名。冲销单继承原方向、器材族和数量，并生成自己的签名。系统在同一事务中锁住原件，验证签名与日期，唯一约束保障每笔原签领只冲销一次。
- 方案起止日均包含。器材族 `f` 在出借馆 `i` 至入借馆 `j` 的有效量 `M[f,i,j] = Σ签领数量 − Σ冲销数量`。冲销按自身生效日入账，因此当期可以出现负向量。伪造签名、原凭据配对错误或边际不守恒会使运行失败。
- 同器材族、无序馆对的相抵量 `max(0, min(M[f,i,j], M[f,j,i]))`，有符号方向差额 `M[f,i,j] − M[f,j,i]`。全馆相抵合计按无序馆对求和一次。CSV 按有向馆对输出，每对两行，其中「双向相抵」在两行各出现一次，汇总时每对取一次。
- 每馆出借为矩阵行和，入借为列和，净流 `入借 − 出借`。全体行和与全体列和都应等于签领减冲销，全馆净流合计应为 0。两向相抵另列供核对，矩阵继续显示两向记账有效量。跨器材族按件数展示汇总，同方向的笙、鼓、锣各保留专属明细。
- 方案版本参数不可变，可复用同一版本重新计算。创建运行时冻结凭据和名录，并在结果中显示快照 SHA-256。发布和 CSV 始终引用该运行，后续补录通过新的运行纳入。

## 运行

使用 Docker Compose，从源码根目录执行：

```bash
cp .env.example .env
docker compose config --quiet
docker compose up --build --wait
docker compose exec -T backend python -m scripts.seed_demo
```

前端 `http://127.0.0.1:18281`，API `http://127.0.0.1:19281/docs`，MySQL `127.0.0.1:17781`。清理本地演示数据可执行 `docker compose down -v --remove-orphans`。本批验收从批次根执行 `bash scripts/verify-project.sh gb-5212`，由脚本分配槽位并清理验收栈。

| 服务 | 技术与职责 |
| --- | --- |
| `frontend` | Nginx 1.27 与原生 HTML/CSS/JS，代理同源 API |
| `backend` | Python 3.11 与 FastAPI，JWS 会话、台账和持久化队列 |
| `worker` | Python 3.11，按队列领取快照，验签、计算并写 CSV |
| `db` | MySQL 8.0，保存凭据、方案、快照、发布与审计 |
| `redis` | Redis 7，登录速率限制与服务依赖检查 |

本地开发时保留同源代理。改动前端后执行 `docker compose up --build --wait frontend`，改动计算或 API 后重建 `backend` 和 `worker`。API 输入可在 FastAPI 文档中交互测试。

`backend/migrations/` 保存初始数据库结构，`backend/scripts/` 管理迁移与演示数据，`backend/src/` 按数据访问、计算、接口和中间件拆分。`frontend/src/` 包含页面、API 客户端、会话和共享表格/表单。数据库、Redis、CSV 分别使用命名卷。

`.env.example` 列出端口、`NETWORK_SUBNET`、Compose 短名、MySQL 凭据、两枚独立密钥与 `SEED_DEMO`。默认子网 `10.221.212.0/24`，可在分配冲突时覆盖。`JWT_SECRET` 是会话密钥，`LEDGER_SECRET` 需在首次签名之前确定并与数据一起持久保管。启动自动应用建表脚本并按 `SEED_DEMO` 载入样本，按自然键补齐，已有编号和签名保留。

共享枚举定义在后端 `src/constants/domain.py`、前端 `src/constants/domain.js` 和数据库 `migrations/001_initial.sql`。`Role` 用于授权、导航席位标签与写表单。`ReceiptKind` 用于登记、验签计算和台账标签。`RunStatus` 用于队列、发布/导出条件及运行与报告状态。

## 已知限制

当前电子签名提供应用内完整性校验和账号归因，所有签名由同一台服务生成。签领全额冲销；部分更正需全额冲销后重签正确数量。订阅保存的是周期与器材族参数，由分析员手动运行；台账界面取最近 500 笔凭据，worker 根据周期读取完整快照。系统核对调借流量，实物库存和归还进度需在馆点另行盘点。
